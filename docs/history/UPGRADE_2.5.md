# Exposure Desk 2.5 upgrade

Version 2.5.0-rc.1 fixes the problems demonstrated by the owner scan of 2.4.0-rc.1 (one seed, one manually approved subdomain, a blocked third subdomain, 45 "pending" resources with nothing queued, false `.json`/`.woff` pages, 48 unattributed deny-proxy events and zero findings) and makes findings useful for financial and critical-secret incidents. Measured results are in [TEST_RESULTS.md](../TEST_RESULTS.md); upgrade steps for saved data are in [MIGRATION_2.5.md](MIGRATION_2.5.md); the change list is in [CHANGELOG_2.5.md](CHANGELOG_2.5.md).

## 1. Domain scope is the default

- Entering `example.com` (or `www.example.com`) authorizes HTTP(S) origins discovered under `example.com`, including nested subdomains, with one acknowledgement at setup: "I own example.com … and all of its subdomains". There are no per-subdomain dialogs.
- The **Scope** fieldset sits under the website box, not in Advanced: *This domain and its subdomains* (default), *Only the exact addresses entered*, and — when a seed is deeper than `www.<domain>` — *This host and hosts beneath it* (for hosting providers missing from the public suffix list). The domain name shown comes from the server (`POST /api/scope/preview`); the browser never guesses it.
- Matching uses punycode registrable domains from the bundled public suffix list (tldts 7.4.16, private suffixes included), never substrings: `example.com.evil.net`, `notexample.com`, other `github.io` tenants and look-alike IDNs are third parties. Scheme and port stay separate budgeted origins.
- One scope policy covers links, scripts, CSS, manifests, source maps, runtime requests, workers, frames, redirects, WebSocket origins and approved browser routes. Domain scope grants eligibility only: every request still needs public DNS, socket pinning, private/metadata blocking (never inherited from domain scope), credential screening, method and destructive-path limits and redirect rechecks. Subdomains are discovered from links only; none are guessed. At most `maxAutoDiscoveredOrigins` (default 50) are admitted, each with the full per-origin limits; shared limits never grow.
- Third-party origins are excluded, summarized once (count, references, first referring resource; 500 origins plus an overflow count) and never counted as websites.
- Opt out with `"domainScope": "exact-origin"` (or the older `"sameRegistrableDomainDiscovery": false`), the radio button, or `cli.js scan --scope exact-origin`. See [exact-origin.config.example.json](../../examples/exact-origin.config.example.json).
- Projects saved before 2.5 keep running exact-origin and show a banner with **Use domain scope for <domain>**, which needs a fresh acknowledgement. Nothing is widened silently.

## 2. Runs and counts

- **Running scan** shows one **Current run** card and a labeled **Previous runs** list (newest first). Each row: project or host, start time, state, short run ID (`#1a2b3c4d`), trigger (Manual start, Queued, Scheduled, Focused retry, Resumed checkpoint, Affected-resource rescan, Synthetic demo, Deployment trigger) and its link ("repeat of #…", "retry of #…"). Records from 2.4 and earlier say "Trigger not recorded".
- Counts are separate: entered seeds, domain groups, authorized origins, origins actually contacted, same-domain origins not scanned, third-party origins excluded, active runs and retained runs. The owner export reads "1 entered seed · 1 domain group (the owner's domain) · 2 authorized origins · 2 contacted". Per-origin budgets are unchanged.
- A blank project name is derived from the first host (`example.com`, `bücher.example`, `a.example.com + 1 more`). Saved projects keep their names; old "Authorized website" runs are labeled by host.
- Start buttons disable while a request is pending and while a run is active. Each start carries an in-memory request ID: a replayed ID returns the first run (`duplicate:true`); a different body with the same ID is refused (`409 request-id-reused`); a start while a run is active returns `409 scan-active` with the active run ID. A repeat of a run that finished in the last two minutes asks for an inline confirmation (no dialog) and is linked with `repeatOf`. Queue buttons are idempotent per render. New API: `GET /api/runs`.

## 3. Discovery without false pages

- JavaScript is parsed once (module → script → tokens-only fallback) and URL uses are taken from real sinks (`fetch`, XHR, axios/jQuery, `import()`, workers, `new URL(x, import.meta.url)`, location assignments, Vite/webpack/Next tables). Each reference records its context and certainty (`confirmed`, `contextual`, `heuristic`, `unresolved`); unresolved expressions stay in the discovery graph only. Downloaded code is never executed outside the isolated browser.
- Bare extension literals (`".json"`, `'.woff'`), object keys, comparisons and dotted identifiers are rejected with counted reasons; `fetch('.json')`, imports, workers and manifest entries are kept. HTML answering an asset URL is classified (SPA fallback, login, soft-404, HTML for an asset) before any browser promotion; explicitly requested routes are never suppressed. Identical content is reused across inspections with distinct provenance.

## 4. Analysis lifecycle and large bundles

- Re-admitting a module no longer resets its analysis; outcomes apply to aliases, including late ones. Every unfinished item ends in an explicit terminal state (`deferred`, `partial`) with its cause (user cancel, project or origin deadline, work-turn or analysis-turn limit, worker failure, engine timeout), so queue, important-uninspected, analyzer states and the verdict agree. A short work turn after a successful download defers analysis (bounded backlog, `analysisBacklogBytes`, default 32 MiB) instead of discarding it.
- Structured discovery covers the first 4 MiB (`maxDiscoveryBytes`); larger documents use a windowed tokenizer. The semantic pool reuses workers, bounds mutation work and reports queue wait, worker startup, parser time, cleanup and the elapsed allocation charge separately. New settings: `workTurnMs` (30 s), `analysisTurnMs` (60 s), `analysisBacklogBytes`, `maxDiscoveryBytes`, `browserBaselineMs` (750 ms).

## 5. Privacy and attribution

What websites see (also shown under **New scan → Before you start → What the websites can see**):

| | Static requests | Browser requests |
| --- | --- | --- |
| User-Agent | `Mozilla/5.0 (compatible; ExposureDesk/2.5)` — no build, OS or user detail. `staticUserAgent: "none"` restores the 2.4 behavior (no User-Agent) | Chromium's real User-Agent; never spoofed |
| Accept-Language | `browserLocale` (default `en-US`) | the same; the isolated browser also uses `browserLocale` and `browserTimezone` (default `UTC`), never this computer's settings |
| Referer / Origin | none | only from authorized pages; Referer cut to the origin (`https://example.com/`); `null` dropped |
| Cookies | none | only cookies set during this visit, only to their own origin |
| Client hints, `priority`, `x-*` | none | dropped; nothing browser-like is fabricated |

- Tradeoffs: the product token makes static requests identifiable (owners can allowlist it); sites can still distinguish automated visits by timing and TLS/HTTP characteristics, so the scanner is not undetectable; sites that vary content by language answer for the configured language; origin-only Referer breaks rare path-based hotlink checks.
- Egress: all target traffic leaves this computer directly to the address Exposure Desk resolved and checked. Websites see this computer's public IP, or the exit address of a system-wide full-tunnel VPN. Windows/PAC proxies, browser-extension VPNs and `HTTP(S)_PROXY`/`ALL_PROXY`/`NODE_USE_ENV_PROXY` are not used (a regression test proves a proxy recorder receives nothing). Target DNS uses the local resolver; a VPN that does not carry IPv6 may leak IPv6 traffic. Upstream proxy support is deliberately not included in this release: a future version would need SOCKS5/HTTP CONNECT to the already checked IP address with no direct fallback, refusing `socks5h`, PAC and system modes.
- Browser hardening: connection to Chromium's own `ws://` debugging endpoint (proxy variables cannot redirect it), an allowlisted environment for Chromium (no proxy variables or API keys; temp folders inside the profile), SharedWorker and the back/forward cache disabled, and `browserStatus.isolation: "checked"` only after the fresh profile, deny proxy, resolver block, minimal environment, own debugging port, routes-before-navigation and SharedWorker checks pass. Cleanup closes the browser through CDP, waits for the process to exit, removes the profile (bounded), and records `cleanup: confirmed|deferred`; profiles left by a crash are swept at the next start. Page-leave beacons and keep-alive requests are drained through the guarded transport, where they are screened and blocked as POSTs.
- Readiness: each browser page records commit, DOM-ready and settle times, causes (`local-rate-limit`, `network-wait`, `blocked-dependency`, `unrouted-dependency`, `dom-not-ready`, `deadline`), work pending at the deadline and blocked dependencies. One bounded extension is allowed only while requests wait in the local rate-limit queue. Analysis backlog no longer aborts page requests.
- Deny-proxy events carry sequence, time and phase and are attributed from CDP network observations (page, frame or worker), header evidence, or pre-navigation timing (background). Hostnames never prove anything; unknown or target-origin events stay visible coverage gaps. The deep-check baseline probes use neutral random 24-character paths.

## 6. Findings for financial and critical-secret incidents

- **Priority** (`priority/1`): urgent, high, review, low or none, with the basis listed. Urgent needs a high-confidence private credential, a complete set (or one missing only an identifier), public exposure and a mapped high-impact capability. Caps: blocked-candidate or local-only evidence → high; test environment, a missing secret component, documentation context or an owner "restricted" record → review; a published documentation example or test vector → low (and moved to the masked dismissed audit); owner-confirmed revocation → review while observed, low once a comparable scan no longer observes it. Technical severity is unchanged.
- **Financial priority** is now strictly financial: urgent only when the level is urgent *and* the possible impact is paid usage, cloud spending or payment/asset access. A GitHub token, PEM key or database password can be urgent with financial priority "none".
- Separate impact rows: possible paid usage, cloud spending, payment or asset access, account takeover, signing/encryption compromise and data access — each followed by "Not established: validity, permissions, restrictions, balances and any loss".
- Environment is aggregated across occurrences regardless of order (production if any occurrence says so; test only if every one does; an owner statement wins). Sandbox hosts (`api-m.sandbox.paypal.com`, `connect.squareupsandbox.com`, …) are test evidence.
- Gitleaks rule prefixes map to real providers and groups (`plaid` → Plaid, payments; `gcp` → Google Cloud, cloud; `private` → signing). New groups: **signing** and **data**.
- New detection (static only; nothing is evaluated, sent or tested): literal keys passed to `jwt.sign`, `createHmac`, `createCipheriv`, `CryptoJS.AES/HmacSHA*`, `crypto.subtle.importKey('raw', …)` and `SignJWT().sign`; signing-secret field names such as `jwtSecret` and `sessionSecret`; Bearer/Basic/`x-api-key` credentials sent to hosts with no mapped provider (named by registrable domain); secrets in unknown SDK constructors; BIP39 seed phrases (12–24 words, every word in the list, valid checksum, not an alphabetical slice; vendored wordlist, see THIRD_PARTY.md); WIF and BIP32 extended private keys (Base58Check, versions, in-range scalar); 32-byte hex keys only beside a private-key name or wallet constructor; Solana 64-byte keys in `Keypair.fromSecretKey`; JWK private members with size checks; PGP private key blocks; PEM structure (`verified`, `encrypted`, `truncated`). Negative controls include transaction hashes, digests, addresses, extended public keys, bad checksums, pixel arrays, published vectors, prose, `jwt.verify`, `createHash`, dynamic `'Bearer ' + token` and publishable keys.
- **Lifecycle**, three independent tracks per finding: *Removed from website* (yes only after a comparable full scan inspected every previously affected URL, or found it gone, and did not observe the value), *Owner-confirmed revoked* (manual record with replacement state; never checked with the provider), and *Rescan completed* (latest outcome: still observed, not observed or uncertain with reasons). A focused rescan can establish "not observed" at the affected URLs. Actions: Report removed, Record owner-confirmed revocation, Rescan affected resources, Full rescan. Affected assets are marked current deployment, previous deployment (reached only through history or manifest replay) or local artifact.
- **Owner record** (environment, restrictions, permission and spend notes): "Owner-reported; Exposure Desk does not verify validity or permissions." It only refines priority.
- **Alerts**: masked, persisted in the workspace (up to 200), shown with a header badge and acknowledgeable — new urgent/high, reappeared, published after revocation, previous deployment still served, incomplete scheduled or deployment runs, rejected or expired triggers. They contain provider, impact kinds, level, masked length, location without query string, run ID and an 8-character correlation prefix, never values. No email, webhook, browser notification or OS service.
- **Deployment-triggered scans** (file-drop, no listener): enable per project in Settings (same authorization as schedules; default at most 24 per day, 10 minutes apart). A build step runs `cli.js trigger --project <id> [--label TEXT] [--assets manifest.json --base URL] [--delay SECONDS]` on this computer; it writes one request into the protected data folder and never opens history, keys or the vault. While Exposure Desk is open, requests are validated (regular single-link files, size, owner, schema, expiry ≤ 24 h), rate limited, coalesced and queued as **Deployment trigger** runs that replay only the exact asset URLs through the normal scope policy; evidence is never saved. For a pre-deploy gate use `cli.js artifacts --directory <build>` (no requests; exit 1 on any private credential). CLI scans accept `--fail-on private-credential|urgent|never`; hosted CI should only keep redacted SARIF and never use `--full-secrets`.
- Reports (JSON, HTML, SARIF) include priority, impacts, qualifiers, lifecycle, owner records and assets; SARIF adds `partialFingerprints["exposureDesk/correlation/v2"]` for stable cross-run matching.
- Rules: `website/2.5.0`; structural data checks remain `exposure/1.0`.

## 7. Remaining limits

- Linux, macOS and ARM were not exercised; the Windows x64 portable package was.
- Measurements use synthetic local fixtures only (frozen corpus `scripts/eval-2.5-corpus.mjs`, digest recorded in `benchmarks/2.5/corpus-freeze.json`). They do not establish accuracy on real websites; see TEST_RESULTS.md for exact counts and the corpus freeze timing note. The frozen large-bundle group (G5) contains a JavaScript syntax error, found after the freeze, so it does not measure split-key reconstruction in either build; the lifecycle regression test covers reconstruction from a valid bundle of the same size.
- Chromium itself still attempts background connections (Google update, sign-in and service hosts); they are denied at the proxy. Candidate privacy flags were measured and did not reduce them, so none were added. Background connections after navigation stay "unknown" by policy.
- Not implemented: owner Burp/HAR capture import, Electrum seed formats, placeholder counting, browser notifications and upstream proxy support. Electrum seeds, encrypted wallet files and hardware-wallet exports are not recognized.
- Worker requests can be attributed from captured worker code (`worker-source`) when Playwright resumes a worker before network observation is enabled; preconnect tunnels to in-scope hosts appear as incomplete unrouted gaps.
