## Bug bounty features: owner decisions

- Audience (owner decision 2026-10-10): bug bounty hunters working from the command line, Linux first, beside the existing website owners. The new features are opt-in; without `--program`, `--concurrency`, `--state`, `--recon`, `--rebuild-sources`, `--format md` or `--submission-bundle`, a scan behaves as in 2.7.
- The hard rules are unchanged: the protected-host block has no override; more than one accepted target and every run with a program file need `--authorized` (or `"authorized": true` in the program file; `program import` never sets it); nothing evades a block (no retries around it, no change of User-Agent, headers, proxy or address); found keys never leave the computer automatically (submission drafts are written offline and masked unless `--full-secrets`, which unmasks only files on disk); all data stays local.
- Live key check (2.9.0): off by default and never automatic. Only a program file with `"liveKeyChecks": { "enabled": true }` turns it on, `"checkAll": true` is a separate permission, and no scan, mass scan or ready option ever checks a key. One read-only identity request per key, one key at a time, to the key's own provider only (recipes for GitHub, GitLab, OpenAI, Anthropic, Stripe, SendGrid and Slack; every other rule reads unknown, `no-recipe`, without a request), with the honest product User-Agent, through the same address guards as a scan. The provider list was taken as the recommended default while the owner was away; the owner should confirm it or name providers to add.
- Concurrency: a `--targets` list without a program file still runs one target at a time by default (as in 2.7); `--concurrency N` allows up to 16, and up to 64 with a program file, whose default is 4. Every target of a mass run shares one analysis memory budget, never multiplied by the number of targets. Above concurrency 1 a memory gate lowers the targets running at once when the scan process is short of memory (ceiling 512 MiB under the ready options), and since 2.9.0 the scan process also runs a full memory collection after large in-process parses add up; waits for capacity the targets share are not charged to their time allowances, and with a program file targets take program-wide request turns in arrival order. Measured figures are under Target lists at scale below.

## Hard rule: protected hosts

Added 2026-10-09 after 2.5.0-rc.1 (not part of the 2.5 packages), between 2.6 P1 and P2 (see `archive/notes/HANDOFF_GOV_BLOCK.md`). Exposure Desk never sends any request to a government, military, intelligence or security-service, law-enforcement, judiciary or intergovernmental-organization website. **There is no override:** no configuration key, CLI flag, environment variable, saved-project field, preset or profile, or dashboard control may disable or narrow it.

- **One module:** `src/protected-hosts.ts` holds the reviewed list and the matcher `protectedHost()`. The list has:
  - the top-level domains .gov, .mil, .int, .va, .cern and .政务;
  - country government, military, police, judiciary, legislature, local-government and international-organization zones, plus US (RFC 1480) and Japanese local-government patterns;
  - well-known bodies on ordinary domains, grouped by country or organization, with one comment each;
  - a public-suffix safety net (bundled tldts data) for gov/govt/gouv/gob/gub/mil/政府 zones the list lacks.

  Hosts are normalized first (lowercase, IDN to punycode, trailing dots, port and userinfo stripped). A host is blocked when it equals an entry or ends with "." + entry.
- **Seeds:** `makeConfig` refuses the whole scan with "Exposure Desk never scans government, military, intelligence or law-enforcement websites: <host>". That covers the CLI (exit 2), the dashboard and API (400, code `protected-host`), saved projects, the queue, routines, deployment triggers, retries and rescans, checkpoint resume, and imported or legacy configs. Saved records that name such a host load unchanged, show the reason and never run. They are never rewritten.
- **Follow-on requests:**
  - `Transport.preflight` covers every send path; `addresses()` refuses before DNS and `openPinned` before a socket. A TLS certificate that names a protected host stops the request before any byte is sent.
  - The scanner refuses at admission (links, redirects, assets, images, sitemaps, source maps, map sections, WebSockets, frontier and retry items).
  - The browser interception layer aborts navigations and subrequests.

  Each refusal is recorded as block kind `protected-host`. It counts like out-of-scope (never incomplete), and reports show the count.
- **Every later part (P2, P3, P4 and any later run) must keep this rule and route any new request path through it.** Call `protectedHost()`, or go through `Transport.one`/`preflight`, before any DNS lookup, socket, proxy hop or browser navigation, and never add a switch around it. The tests in `test/protected-hosts.test.ts` and `test/protected-hosts-browser.test.ts` must stay green.
- **Changing the list:** the list grows only in code, through a reviewed change with one comment per entry. Never contact a listed site, not even to test.
- **2.7.0:** every `scan --targets` line passes through `protectedHost()` before any request, with no override. The website-host check added in 2.7.0 (see MIGRATION_2.7.md) runs after it; a protected host keeps its own message.
- **2.8.0:** a program file can only narrow what a scan contacts. The protected-host check runs before the program scope on every `--targets` line and every request; an in-scope program rule that names a protected host is refused (exit 2, before any request), and `program import` refuses such rules and lists them on standard error. Recon lists, source-map rebuilding and submission drafts work offline on what the scan already fetched and send no requests; recon classifies a protected host as out of scope. No 2.8 option (concurrency, resume, program settings, the analysis time factor) loosens the rule.
- **2.9.0:** `politie.be` (Belgian police) and `policia.pt` (Portuguese police portal) joined the list with their subdomains (lookalikes such as `notpolitie.be` stay unblocked; covered by a test). The live key check's one request goes through the same guard before DNS, with no override, and its provider hosts are a fixed allowlist. The new host validation of discovered URLs (`invalid-url`) runs after the protected-host check, so a protected host keeps its own block kind. Popups are never loaded; a popup's in-scope page URL joins the scan under the same rules. No 2.9 option loosens the rule.
- **Known limits:** unlisted bodies on ordinary domains, bare IP addresses and CNAME aliases are not detected. HTTPS aliases are caught only through the server certificate, after the handshake. See the module header and USER_GUIDE.md.

## Ready options: owner decisions and defaults

- Standard + Normal is Recommended and the default for the scan page, new projects and a CLI scan without a preset, option, configuration file, checkpoint or sizing flag. 2.5 ran legacy `thorough` by default on the CLI; `--preset thorough` keeps that.
- Low-impact visits one query-string variant per path and shows the rest as **Limited by profile**, not as a gap (owner decision, 2026-10-09). A Low-impact run with a real gap stays incomplete and also says "Also limited by profile".
- Saved settings from older versions keep their stored numbers and are never re-mapped silently; the owner switches them on their cards.
- Websites at once (fixed in P4 after the first matrix run): a ready option starts at most its websites at once; further websites wait for a free slot, so each website's time allowance starts with its own first request and Low-impact keeps one connection per website. Before the fix every website started together, and 10 websites shared the scan's analysis throughput inside one allowance (Standard + Normal ×10 found 50 of 70 in-scope keys; Low-impact ×10 opened one connection per request). 2.5 configurations keep their round-robin over every website.
- Deployment paths while the browser is busy (fixed in P4 after the small-computer matrix): a ready-option website whose browser turn waits for a browser slot other websites hold probes its deployment paths meanwhile, so a small computer (one browser website at once) no longer loses `/.env` and `/config.json` to the soft deadline. A free browser keeps the order browser pages, then deployment paths; 2.5 configurations are unchanged.

## Known gaps and honest caveats

- **Live key check: local stand-ins only.** Each provider recipe was tested against a loopback stand-in that answers like the provider's documented identity endpoint; real provider responses, rate limits and error bodies were never seen. A changed provider endpoint or answer reads **unknown**, never **live**. Many programs forbid testing found credentials, so it stays off unless a program file turns it on. The provider list (GitHub, GitLab, OpenAI, Anthropic, Stripe, SendGrid, Slack) awaits the owner's confirmation.
- **Target lists at once: speed and shared waits.** Waits for capacity the targets share do not use a target's time allowances, so every target completed at 1 to 64 at once (200 Quick check targets: 2238 s one at a time, 592 s at 4, 207 s at 16 and 173 s at 64 with a program file; 2.8.0: 2272, 618, 234 and 206 s). With a program file the program's request limiter sets the pace. Since 2.9.0 it grants waiting requests in arrival order, so the longest single wait fell from 23.8 s to 3.1 s, but on this Windows computer it still granted about 25 requests per second against its nominal 50 while 64 targets waited (2.8.0: about 21). Because these waits use no allowance, this costs wall time only. `summary.sharedWaitMs` counts every shared wait summed over targets, so it is not wall time (docs/JSONL.md); since 2.9.0 `sharedWaitByCause` splits it into analysis, parser, preflight and program-slot waits. In these runs almost all of it was preflight screening (221 of 222 s at 16 at once), which does not take part in the fair request queue: it is short per request and was left alone for 2.9.0.
- **Memory in a mass run.** The analysis memory setting is one budget for every target of the run and was never exceeded. It does not cover the scan process itself, which holds every running target's state. 204 MiB one target at a time, 309 MiB at 4, 329 MiB at 16 and 357 MiB with 64 targets at once (program file), and 379–390 MiB with 16 large-bundle targets at 1 to 16 at once, while the analysis budget stayed at 256 MiB. The gate described next held a target start 32 times at 64 at once and never at 4 or 16. Above concurrency 1 a memory gate starts the next target only while the scan process's memory leaves room under 512 MiB (the ready-option ceiling); since 2.9.0 a full memory collection after large in-process parses keeps targets with large bundles under it as well (2.8.0 peaked at 557–577 MiB with 16 such targets, see CHANGELOG_2.9.md). `summary.memory` is emitted only from 2 targets at once up.
- **Timing-dependent tests.** On build 2.9.0+b251a3ea63449d85 the final suites passed on a quiet machine (above). Under heavy outside load (a CPU-bound job outside the suite runner, at or above 95 % CPU) three tests failed in the sanity suites: two browser tests whose Chrome did not confirm its exit within the 3 s cleanup bound, and one mass-scale test whose analysis turn hit its limit; each passed when rerun alone (`benchmarks/2.9.0/browser-attempts.json`). One dashboard feedback test (`completeness-browser`, adaptive JSON / scoped feedback) lost a just-opened `details` element to a re-render once on a loaded Linux runner during 2.9 development; it is worth hardening. The 2.8 timing fixes (CHANGELOG_2.8.md) and the first-come, first-served engine and large-text lanes (since 2.7.0, `test/engine-lanes.test.ts`) are unchanged.
- **Page-leave guard.** 2.9.0 closes the gaps 2.8.0 listed: the guard survives `document.open`, a removed or detached frame never runs the page's page-leave handlers, a navigation the page starts drains the leaving documents' handlers while routing applies, popups are never loaded, and requests a page starts after its inspection are aborted. Trade-off: the page-leave handlers of a document that leaves without a network request (a removed frame, `about:blank`, `javascript:` or `srcdoc`) no longer run, so anything only they would reveal is not seen. Playwright's `page.evaluate` runs with a user gesture, so the scanner's scroll, snapshot and drain steps give pages transient user activation (which is how a page can open a popup at all); the guard tests account for this.
- G5 of the frozen 2.5 corpus still does not measure large-bundle reconstruction (its bundle has a syntax error, see the 2.5 notes in TEST_RESULTS.md). The G5F group parses the corrected bundle, but its split key is still not found: following webpack's cross-module constant exports was left out of 2.9.0.
- Memory: since 2.7.0 the setting (at most 512 MiB under the ready options; a program file's `analysisMemoryMb` may raise it to 2048 MiB) is one first-come, first-served budget for the parser and large-text worker heaps, and each worker runs in its own process and holds its heap limit until it has ended. Not covered: the scan process itself, each worker process's own runtime (about 40–56 MiB), the small finding-triage worker, the isolated browser and the engine process. Measured in the 2.9.0 matrix: scan-process peak 280–324 MiB on the 1.25 MB bundle fixture (2.8.0 records: 248–334 MiB) and at most 324 MiB in any 2.9.0 row; 65 analysis processes, heap limits at most 512 MiB at once, 0 out of memory; scan peak plus analysis-process peaks at most 740 MiB (2.8.0 records: 707 MiB), an upper bound. In a target list the scan process grows with the targets running at once (see Memory in a mass run above). Still open from 2.7.0: on 256 MiB with one parser, a large-text check ends the idle parser, and the next parser job starts a new one (about 0.1 s, about once per scan; measured, not changed).
- Speed: analysis takes about 0.6 s per resource, so the Normal options are bounded by analysis rather than by their traffic limits, and Quick check + Normal for 10 websites is close to its per-website soft deadline (deferrals depend on timing). Since 2.8.0 a slower computer scales the analysis time limits by its measured time factor (1 to 4; `EXPOSURE_ANALYSIS_TIME_FACTOR` sets 1 to 8), but never a scan's or website's duration limit. Low-impact reconnects after more than 4 s idle.
- Most fixture runs end **incomplete** on purpose. The fixtures plant pages deeper than each option goes, an encoded blob over the inspection limit and browser requests to unrouted hosts, and the runs report those as gaps rather than hiding them. A discovered URL with an invalid host (`invalid-url`, refused since 2.9.0) is informational since 2.9.1: it is still listed, but it no longer makes a run incomplete.
- Detection: the external corpus's 3 false positives are policy cases (two Stripe test-mode keys, one OpenAI documentation example) and are labelled test-environment or lower priority. The 31 new rules were ported from Gitleaks (MIT) and Nosey Parker (Apache-2.0) with bounded quantifiers and tested on synthetic fixtures only; an old-vs-new comparison over 529 inputs found no change in existing results.
- Scope limits:
  - Tenant providers that are on neither the public suffix list nor the curated list of 80 keep the wider registrable domain.
  - The protected-host list misses unlisted bodies on ordinary domains, bare IP addresses and CNAME aliases. The owner should review the list.
- Platforms: Windows x64 measured on one computer; Linux x64 tested only on GitHub-hosted Ubuntu runners (pass/fail, no timing or memory figures; other distributions unverified). macOS and ARM are not supported yet, and an uninstalled source bootstrap was not exercised. All measurements are synthetic and local and make no claim about accuracy or speed on real websites. Still not implemented (as in 2.5): owner Burp/HAR capture import, Electrum seeds, encrypted wallet files and hardware-wallet exports, browser notifications, upstream proxy support.
- 2.9.0, like 2.8.0, was prepared on the local evidence above, without the owner's own trial. The owner should try the ready options on their own sites, the bug bounty workflow on a program they joined, and the live key check only where a program permits it, before showing results to anyone.
